# Tomcat 服务 502 与 503 错误处置指南

## 概述

接入层使用 Nginx 反向代理，把请求转发到 oa-app01 至 oa-app04 的 8080 端口。502 表示网关无法从上游获得合法响应，通常是连接层问题；503 表示上游暂时不可用，更多与容量、重启或维护状态有关。
接入层配置了健康探测与自动摘除，节点异常时流量会自动转移到健康节点，但探测间隔内的请求仍可能拿到错误码，需要结合日志判断故障范围。

## 故障现象

502 的典型特征：

- error.log 出现 connect() failed (111: Connection refused) while connecting to upstream，多指上游端口未监听或拒绝连接；
- 出现 upstream prematurely closed connection while reading response header from upstream，说明连接建立后被上游主动断开；
- 间歇性 502：部分请求成功、部分失败，多与个别节点异常或连接被中途关闭有关；
- 浏览器看到 502 Bad Gateway，而静态资源仍可访问，说明接入层本身正常。

503 的典型特征：

- 浏览器提示 503 Service Temporarily Unavailable；
- 上游线程池被打满，请求长时间排队后返回；
- 节点正在重启或处于维护窗口，健康检查未通过。

## 排查步骤

1. 划分故障面：对各应用节点直连检查，如 curl -I http://10.20.10.21:8080/portal/，确认单节点还是全部节点异常；
2. 查看接入层日志：tail -n 100 /var/log/nginx/error.log，统计 502 出现频率；
3. 检查应用进程与端口：确认 8080 是否监听、进程是否健在；
4. 查看连接状态：ss -s 关注 TIME_WAIT 是否异常堆积；
5. 检查线程池与排队：连续 5 分钟出现排队即视为容量问题；
6. 复核时间窗口：对照变更记录与维护日历，确认是否处于发版或维护窗口。

## 常见原因

502 常见原因：应用进程退出或崩溃；端口未监听；上游处理时间超过 proxy_read_timeout（默认 60 秒）触发中断；安全组或防火墙拦截；keepalive 长连接被中途关闭。

503 常见原因：全部上游节点被标记为不可用（如 max_fails 触发）；Tomcat 处于重启或维护窗口；上游线程池被打满导致新请求直接被拒绝。

| 错误码 | 常见日志关键字 | 指向 |
|---|---|---|
| 502 | Connection refused | 上游未监听或拒绝连接 |
| 502 | upstream prematurely closed connection | 上游处理中断并断开 |
| 503 | service unavailable | 上游整体不可用或维护中 |
| 504 | upstream timed out | 上游处理超时 |

## 处置步骤

- 单节点 502：先在 upstream 配置中注释掉该 server 行，执行 nginx -s reload 摘除流量，待恢复后再挂回；
- 全量 502：按应用启动失败思路排查进程与端口，必要时重启；
- 回滚优先：若错误码在发布后集中出现，优先回滚到上一版本，再排查细节；
- 持续 503：确认是否处于维护窗口；若为容量问题，临时把 maxThreads 从 200 调到 300 并配合限流；
- 连接积压：优先恢复服务，再分析连接泄漏与超时配置。

## 预防措施

- 应用节点至少双活，避免单点；
- 健康检查接口固定为 /portal/health，接入层按 5 秒间隔探测；
- 配置 proxy_next_upstream，上游失败时自动重试其它节点；
- 每次发版按灰度顺序滚动重启，单批不超过一半节点，确认 5xx 回落后再继续；
- 接入层与应用的超时参数保持匹配，避免一侧等待过久放大故障；
- 监控 Nginx 5xx 比例，超过 1% 持续 3 分钟即告警。

## 附录

- 快速判断：能连上但被断开多为上游处理异常；连不上多为进程或端口问题；能连上但长时间无响应先看线程池与超时。
- 流量摘除与挂回务必成对操作，避免节点被永久遗忘。
- 涉及配置修改的操作均需在变更窗口执行，并做好回滚准备。
- 常见误判：静态资源走单独目录，页面打不开不代表静态资源有问题，先分别验证再下结论。
- 复盘要求：每次错误码处置完成后 24 小时内输出时间线与改进项。
