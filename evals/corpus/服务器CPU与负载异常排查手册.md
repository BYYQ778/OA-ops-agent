# 服务器 CPU 与负载异常排查手册

## 概述

负载异常大体分三类：CPU 真忙、IO 等待、内核态开销。判断时先看负载与处理核数的比值，再看消耗集中在哪个维度，避免只凭单一数值下结论。
处置前先确认持续时长与影响面：短时冲高且自动回落的多为任务叠加，持续数小时不回落的一般伴随死循环或回收恶化。

## 故障现象

- 页面与接口响应明显变慢，出现批量超时；
- 主机上出现阶梯状的耗时抬升，任务排队时长变长；
- 监控告警 CPU 使用率超过 90% 且持续 10 分钟以上；
- 登录、提交等操作排队，偶发 502 或请求被拒绝。

## 排查步骤

1. 执行 uptime 查看 1、5、15 分钟平均负载；负载持续超过核数的 2 倍需要立即介入；
2. 在 top 中按 P 键按 CPU 排序，记录 %us、%sy、%wa、%id 四项；
3. 执行 vmstat 1 10 观察 r（运行队列）、b（阻塞进程）、si/so（换页）、wa（IO 等待）；
4. 进程定位：top -Hp <pid> 找到高占用线程；ps -eo pid,pcpu,pmem,cmd --sort=-pcpu | head -10 找到高占用进程；
5. Java 应用另看：jstat -gcutil <pid> 1000 确认 Full GC 是否频繁；
6. 对照变更与任务日历：确认是否存在刚上线的脚本、刚调整的参数或集中执行的批量任务。

## 常见原因

- 死循环或无限重试：单核使用率接近 100%，%us 高、负载缓慢抬升；
- 频繁 Full GC：JVM 吃掉大量 CPU，%sy 偏高且 FGC 持续增长；
- 异常进程：失控脚本或植入程序，占用高且命令路径可疑；
- 参数调整引发重试风暴：连接超时与重试参数被同时收紧后，失败请求互相放大；
- IO 等待：%wa 高、load 高但 CPU 空闲，多为磁盘故障或刷盘压力；
- 批量任务叠加：定时导出与大查询在高峰期集中执行。

## 处置步骤

1. 先止损：把压力节点从接入层摘除，或对非核心接口限流；
2. 按 PID 定性：异常进程直接终止并排查来源；Java 应用确认为 GC 问题则按内存手册处理；批量任务改到低峰重跑；
3. 保留现场：top -b -n 1 结果、jstack <pid> 线程栈各留一份；
4. 观察 30 分钟：确认负载与响应时间恢复正常，再逐步恢复流量。
处置坚持先止损后定位：摘除节点、限流与降级能立刻减小影响，切勿在负载高企时直接在生产节点做长时间分析。恢复流量后继续观察 30 分钟，确认负载与响应时间均稳定再结束处置。

## 预防措施

- 对 load、CPU 使用率、%wa 分别设置告警阈值；
- 对高占用进程建立基线清单，定期核对进程与命令行，出现陌生条目立即上报；
- 批量任务固定错峰执行，避开上午与月末高峰；
- 每季度复盘一次历史告警，把误报率高的阈值调整到合理区间；
- 定期复查 JVM 参数与 GC 表现，结合压测调优；
- 收紧脚本执行权限，异常进程第一时间可追溯。

## 附录

| 指标 | 正常表现 | 异常指向 |
|---|---|---|
| load 与核数比值 | 小于核数 | 持续大于 2 倍需介入 |
| %us | 稳态有回落 | 长期贴近 100% 指向死循环 |
| %sy | 平稳 | 持续偏高怀疑 GC 或系统调用异常 |
| %wa | 个位数 | 明显升高指向磁盘 IO |

判断顺序建议：先看负载与核数比值，再看维度分配，最后落到具体进程。
- 常用工具口径：uptime 看趋势；top 看维度；vmstat 看队列与换页；pidstat 看单进程；jstack 看线程栈。
