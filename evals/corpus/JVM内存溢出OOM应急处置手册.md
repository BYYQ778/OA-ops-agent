# JVM 内存溢出 OOM 应急处置手册

## 概述

应用以 Java 8 运行在 Tomcat 内，堆参数为 -Xms4096m -Xmx4096m。内存溢出主要分两类：堆内存溢出（Java heap space）与元空间溢出（Metaspace），前者多与对象堆积有关，后者多与类加载有关。
运行环境使用 G1 回收器，日常关注暂停时长与回收后堆占用能否回落，任何参数调整都需要在备用节点先验证。

## 故障现象

- 日志出现 java.lang.OutOfMemoryError: Java heap space；
- 日志出现 java.lang.OutOfMemoryError: Metaspace；
- 应用响应变慢直至无响应，Full GC 频繁但回收效果差；
- 监控面板显示 Full GC 次数突增，接口耗时同步升高；
- 日志中 GC 停顿占比持续上升，业务线程被拖慢；
- 伴随出现 502 或请求批量超时，CPU 因 GC 升高。

## 排查步骤

1. 确认溢出类型：grep -i "OutOfMemoryError" /opt/tomcat/logs/catalina.out，区分堆与元空间；
2. 观察 GC：jstat -gcutil <pid> 1000 10，重点看 O 列与 FGC、FGCT 的增长速度；
3. 查看堆概况：jmap -heap <pid>，对比各分区使用率；
4. 查找大对象：jmap -histo:live <pid> | head -20，确认占用最高的类；
5. 备用工具：jcmd <pid> GC.heap_info 与 jcmd <pid> GC.class_histogram；
6. 系统侧：top -Hp <pid> 观察 GC 线程的 CPU 占用。
排查时先确认是否由同一时段的批量任务触发的临时高峰，排除一次性因素后再按溢出类型深入分析。

## 常见原因

- 内存泄漏：集合只增不减、监听器未注销、连接未归还导致对象无法回收；
- 大对象：一次性加载大报表或全量数据导出；
- 缓存无上限：本地缓存未设置淘汰策略；
- 报表中间结果与导出文件常驻内存，占用随数据量持续升高；
- 堆设置偏小：数据量增长后 -Xmx4096m 不再足够；
- Metaspace 泄漏：热部署反复加载类，旧类加载器无法释放。

## 处置步骤

1. 保留现场：确认已开启 -XX:+HeapDumpOnOutOfMemoryError，且 -XX:HeapDumpPath=/opt/dumps 下已生成堆转储文件；文件可能有数 GB，先确认磁盘空间充足；
2. 应急重启：执行 systemctl restart tomcat，尽量避开业务高峰，并确认没有正在处理的流程实例；
3. 参数调整：确属容量不足时，把 -Xmx 由 4096m 提高到 6144m 后重启观察，堆上限不要超过物理内存的 70%；
4. 若判断为泄漏：把堆转储文件交给研发用 MAT 分析，同时临时加大堆争取时间；
5. 观察 24 小时：用 jstat 复查 O 使用率与 Full GC 频率是否回到正常水平；
6. 容量复盘：恢复后核对最近一个月的堆占用趋势，评估是否提前安排扩容或代码优化。
若无法立即判断类型，按保留现场、限制入口流量的顺序操作，再决定是否重启。

## 预防措施

- 打开 GC 日志，便于事后还原停顿与回收情况；
- 必须配置 -XX:HeapDumpPath=/opt/dumps，保证溢出时有现场可查；
- 每季度结合业务峰值做一次参数评审，重点复核堆上限与元空间设置；
- 监控 Full GC 次数，达到每小时 5 次以上即告警；
- 每次版本发布前做一轮峰值压测，重点观察堆增长曲线；
- 与业务方确认大报表与导出任务的执行时段，避免与其他批处理叠加，控制瞬时对象峰值。

## 附录

| 命令 | 用途 | 要点 |
|---|---|---|
| jstat -gcutil | 查看各分区回收比例 | 关注 O 与 FGC |
| jmap -heap | 查看堆分区概况 | 对比使用率 |
| jmap -histo:live | 对象占用排名 | 结合 head 使用 |
| jcmd | 替代部分 jmap 场景 | GC.heap_info 与 GC.class_histogram |

- 参数口径：-Xms 与 -Xmx 保持一致可减少动态扩缩带来的抖动；MetaspaceSize 建议显式设置为 256m 起步。
- 应急口径：重启属于止损手段，不能替代根因分析；未留下堆转储的重启会让排查失去线索。
- 沟通要求：判定为泄漏后同步研发与业务方，明确分析时限与临时缓解手段。
